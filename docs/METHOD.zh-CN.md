# Agent Project OS 方法论

[English](METHOD.md)

Agent Project OS 是面向长期 AI 原生工程的本地优先运行方法，服务于同时使用多个模型和客户端的个人开发者与一人团队。

## 运行总则

> 仓库保存事实与策略，Agent 提交结构化变更，确定性 CLI 负责校验，控制面由工程证据重建，人保留最终决策权。

组织结构为 `Founder → Agent CEO → PMO → accountable 项目 PM → 工程 Agent`；Agent HR 与 PMO 并行，负责角色、能力、Prompt/Skill 版本、评测、晋升、回滚和退役。这套金字塔是产品的组织层，既有 Task/Evidence/Decision/Handoff 协议是其 Project Kernel。

## 八项原则

1. **本地优先。** 核心运行不依赖云服务或数据库。
2. **仓库原生。** Git 跟踪文件是可移植事实源。对话、客户端任务状态和模型记忆只是上下文，不是已接纳状态。
3. **联邦自治。** 各项目拥有自己的领域状态；组织注册表只登记身份、优先级、owner、生命周期、PM 分派、关系、接口、监督策略和验证命令，绝不复制任务账本。
4. **证据门禁。** 声明、产物、确定性验证、消费者接纳和外部结果是五种不同事实（E0–E4）。
5. **人工权威。** 不可逆动作、生产、权限、资金和公开发布必须显式人工批准。
6. **运行时中立。** runtime、client version、model ID、provider hint 分别记录。
7. **适配器隔离。** 客户端专属指令、Hooks、Plugins、worktree 和 Agent Teams 不进入核心协议。
8. **控制面可重建。** CEO/PMO/HR 状态视图与索引只是投影；删除后必须能从项目文件、组织记录、Git、验证证据和接纳回执重建。

## 三条状态边界

- **提案态：** Agent 变更请求位于 `inbox/`，等待策略或人工复核。
- **接纳态：** `tasks/`、`evidence/`、`decisions/`、`handoffs/` 和 `receipts/` 中的当前实体文件。
- **外部结果：** 来自真实外部世界的 E4 证据，不能由代码完成或部署成功推断。

这组边界避免客户端显示“完成”后，生成式声明就自动变成组织事实。

## 运行闭环

1. CEO 与 PMO 从组织注册表、优先级、到期监管、已接纳子 PM 报告和例外队列完成定向。
2. accountable PM 从项目的 `AGENTS.md`、manifest、任务、证据、已接纳决策和最新交接完成定向。
3. 固定一个结果和验收标准；跨项目接口变更前计算受影响工程。
4. 客户端支持时，用分支/worktree 隔离重叠代码改动。
5. 按策略提交或应用最小结构化状态变更。
6. 运行确定性验证，记录实际证据等级，并在需要时取得消费者接纳。
7. 提交有边界的项目报告；PMO 在不复制项目状态的前提下接纳或拒绝。
8. Agent HR 评测能力资产，并通过独立复核提出版本化升级。
9. 重建 CEO/PMO/HR 投影，并交接未完成工作。

## 本方法不做什么

它不运行模型，不替代 Git 托管或 Issue 系统，不提供沙箱，不授予无人值守生产或晋升权限，不实现 RBAC/云同步，也不要求不同客户端表面功能完全一致。本地只读大盘可以消费协议，但不能成为第二事实源。
